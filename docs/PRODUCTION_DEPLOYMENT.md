# Production deployment

## Reference architecture

```text
Browser / CLI / CI / remote Agents
                 │ HTTPS / WSS
                 ▼
          Caddy reverse proxy
                 │ private HTTP, trusted proxy only
                 ▼
            Control Plane ───── Artifact storage
                 │
                 ▼
             PostgreSQL
```

`deploy/production/compose.yaml` assigns the proxy `172.30.0.5` and trusts only
`172.30.0.5/32` for forwarded headers. PostgreSQL and the control plane are not published. If the
subnet overlaps another Docker network, change the subnet, static addresses, and trusted proxy CIDR
together. Trusting the entire bridge would let another compromised container spoof client details.

## Configuration and secrets

The template separates three concerns:

- `control-plane.yaml` contains reviewable application policy;
- `.env` contains non-secret deployment/runtime selections; and
- `secrets/` contains mounted secret values generated by `lab-platform init`.

Configuration precedence is CLI override, environment, YAML, then defaults. Production uses
`LAB_DATABASE_URL_FILE` and `LAB_SECRET_KEY_FILE`; it never writes either secret into YAML or image
layers. Do not expose secrets through `docker compose config`, shell history, diagnostics bundles,
or support tickets.

The database URL secret should use the internal service name and require the intended transport:

```text
postgresql://lab_platform:PERCENT_ENCODED_PASSWORD@postgres:5432/lab_platform
```

For an external database, use `sslmode=verify-full`, a trusted CA, least-privilege credentials,
connection limits, and provider-native backups. `READ COMMITTED` is the documented transaction
isolation baseline; application serialization/advisory locks protect coordination writes.

## TLS and proxy behavior

Caddy obtains and renews certificates for `LAB_PUBLIC_HOST`. The external URL in
`LAB_PUBLIC_URL` must be the same HTTPS origin used by the dashboard and Agents. The control plane
accepts forwarded information only from the configured proxy address. WebSockets require no
separate route in Caddy.

An existing organisation proxy may replace Caddy. Preserve HTTPS/WSS, request IDs, streaming/SSE,
WebSocket upgrade, upload limits, timeouts, and client address headers; set its exact source CIDR
as the only trusted network. Direct control-plane TLS is also supported, but do not enable direct
TLS and proxy termination simultaneously.

## Preflight and startup

1. Verify DNS, ports, time synchronization, free space/inodes, and image signatures.
2. Review `.env`, configuration, resource limits, rate policies, and retention.
3. Run `config validate`, `production-check`, and `db status`; apply the explicit migration, then
   require a clean `db check` before starting the control plane.
4. Start services and wait for control-plane readiness.
5. Bootstrap the owner through the CLI, not SQL.
6. Enroll a SimLab Agent and run a smoke workflow.
7. Create and verify the first backup; record its off-host location.

```console
docker compose pull
docker compose run --rm control-plane config validate --config /etc/lab-platform/control-plane.yaml
docker compose run --rm control-plane production-check --config /etc/lab-platform/control-plane.yaml
docker compose run --rm control-plane db status --config /etc/lab-platform/control-plane.yaml
docker compose run --rm control-plane db migrate --config /etc/lab-platform/control-plane.yaml
docker compose run --rm control-plane db check --config /etc/lab-platform/control-plane.yaml
docker compose up -d
curl --fail https://lab.example.com/health/ready
```

Production `serve` repeats the dependency-aware production preflight and refuses to start when
the database/schema, secret strength, TLS/proxy posture, artifact storage, OIDC secret, resource
limits, or public API rate limits are unsafe. The explicit commands remain useful because they
report failures before a Compose replacement is attempted; they are not a bypassable alternative
to the startup gate.

## Persistent data

The Compose volumes are `postgres-data`, `artifact-data`, `caddy-data`, and `caddy-config`.
Container replacement must not delete them. A database-only snapshot is not a complete platform
backup: artifact bytes and the backup manifest/checksums must remain consistent with metadata.

S3-compatible storage is preferred when artifact volume size, durability, or off-host recovery
outgrows local storage. Buckets remain private; encryption, versioning, lifecycle policies, and
backup replication are infrastructure responsibilities.

## Operations and shutdown

Use `/health/live` only for process restart decisions and `/health/ready` for traffic admission.
Scrape `/metrics`, retain structured JSON logs, and alert on database/storage readiness, background
worker failure, queue depth, failed workflows, disconnected Agents, and capacity.

Operational lifecycle records use the `event_type` and `event_payload` JSON fields. The supported
catalogue is `DATABASE_MIGRATION_STARTED`, `DATABASE_MIGRATION_COMPLETED`, `BACKUP_STARTED`,
`BACKUP_COMPLETED`, `BACKUP_FAILED`, `RESTORE_STARTED`, `RESTORE_COMPLETED`,
`RETENTION_DELETION`, `STORAGE_UNAVAILABLE`, `VERSION_INCOMPATIBLE`, and
`AGENT_UPGRADE_AVAILABLE`. Migration, backup/restore, storage, and version records deliberately use
the off-host process log because they can occur while the application database is unavailable,
being migrated, or being replaced. Artifact `RETENTION_DELETION` is also written durably to the
audit table in the same transaction that commits the tombstone.

Compose gives the control plane a 45-second stop grace period. During graceful shutdown it marks
readiness false, stops new work, drains requests/workers, persists queues, and closes gateway and
database connections. Do not use `docker kill` for normal maintenance.
